## 0. 先确认这层收益的天花板

revmc 消掉的是**解释器 dispatch 开销**（opcode 循环、栈边界检查、跳转表）。但真实链上负载里，一笔 ERC20 transfer 或 Uniswap swap 的时间大头通常是 state 访问（SLOAD 打到 DB/trie）、keccak、以及 journal 记账，纯 dispatch 占比往往没有直觉上那么高。

Amdahl 很残酷：如果 dispatch 只占整体执行时间的 15%，revmc 就算把它干到 0，全局也就快 15%。而你为此要引入一个后台编译器、一套缓存、一个共识正确性风险面。

所以**第一步不是写 TieredExec，是 profile**：在你们真实的 block 回放负载上，量出解释器 dispatch 占总执行时间的比例。这个数字决定了后面所有设计的预算。低于 20% 的话，这套东西大概率不如先去优化 state 访问路径。

另外顺手确认一件事：**revmc 当前的维护状态和 API 稳定性**。我记得它一直挂着 experimental/WIP 的标签，Paradigm 那边后来投入减少了。这个我不确定现在的情况，但它是整个方案的地基，值得你先花十分钟确认，别设计完了发现上游停更两年。

## 1. 计数指标：`count` 不该数调用次数

这是草稿里我认为最该改的一处。

调用次数和"值不值得编译"关联很弱：一个被调 1000 次、每次 200 gas 的 proxy，和一个被调 20 次、每次跑 500 万 gas 的数学库，前者会先撞阈值，但后者才是 revmc 真正能赚钱的目标。

**改成累计执行的 opcode 步数**（不是 gas）。理由：
- gas 会严重高估 storage 密集型合约——cold SLOAD 是 2100 gas，但它是 DB-bound，恰恰是 JIT 帮不上忙的部分。
- 步数直接正比于 dispatch 工作量，也就是 revmc 真正消掉的那块。
- 成本几乎为零：解释器主循环里一个局部变量自增，每个 call frame 结束时汇总一次，没有原子操作。如果 revm 没现成暴露，加这一行也很便宜。

顺带一个安全性副作用：按步数计数天然抗 spam——刷一个 45 字节的 minimal proxy 一百万次，累计步数依然很低，不会污染编译队列。

## 2. 阈值：别拍数字，先量分布

"50" 这种数拍出来没有依据。做法应该是：先把计数器加上（不接编译器），跑几千个真实 block，把每个 code hash 的累计步数分布 dump 出来，看拐点在哪。

我的预期是这个分布**极度长尾**——主网上少数几十个 code hash（USDT/USDC/WETH/Uniswap pool/router/multicall）覆盖绝大部分执行量。如果确实如此，好消息是**阈值不敏感**：在一个很宽的区间里选，得到的热集合几乎是同一批。你不需要精调，只需要避开两端。

真正需要约束的不是阈值本身，而是它派生出来的两个量：**稳态下每秒 tier-up 的次数**（决定编译器 CPU 占用）和**缓存条目数**（决定内存）。按这两个指标反推阈值。

再补两个硬性过滤，跟阈值无关：
- **initcode 直接跳过**——构造函数只跑一次，编译纯亏。
- **字节码长度地板**（比如 < 200 字节不编译）——proxy 这类合约调用极频繁但几乎不干活，编译收益被调用开销吃掉。

## 3. 同步还是异步：只能异步，不要留同步选项

这个没有权衡余地，两个理由：

**DoS**：同步编译意味着攻击者可以构造一个 LLVM 编译特别慢的合约（超大字节码 + 病态 CFG），刚好把它推过阈值，让某一笔交易卡住几百毫秒到几秒。对出块节点这是直接的活性攻击。

**非确定性**：同步编译让交易执行耗时依赖本地缓存状态，不同节点的缓存不同。任何基于 wall-clock 的逻辑（出块 deadline、打包多少笔）都会跟着分叉。

异步之后，编译从"延迟风险"降级成"资源风险"，用这几条兜住：编译队列有界、in-flight 集合去重（同一个 code hash 别排两次）、按累计步数排优先级而不是 FIFO、编译线程数限死 1–2 个并调低优先级（LLVM -O2/-O3 跑大合约能把一个核吃满接近一秒）。

## 4. 缓存 key 不是 CodeHash——reorg 不是你的问题，硬分叉才是

先说 reorg：**你已经解决了，只是没意识到。**

编译产物是 bytecode 的纯函数，而 code hash → bytecode 是 keccak 定义的、永久不变的映射。reorg 会改变"哪个地址上有什么代码"，但绝不会改变"code hash X 对应什么字节码"。所以按 code hash 索引的编译缓存**天然是内容寻址的，reorg 后不需要任何失效处理**。最坏情况是你手上留着一份回滚分支上某合约的编译产物，占点内存，LRU 会把它淘汰掉。计数器被回滚分支污染也一样无害——它本来就是个启发式。

（反过来说：如果你当初按 **address** 建索引，reorg、proxy 升级、CREATE2 selfdestruct 后重部署，每一个都会给你一个用错代码的共识 bug。所以这个选择要守住。）

真正的失效来源是**硬分叉**。编译产物把当时的 gas 表和 opcode 语义烤进了机器码里。任何 gas repricing（EIP-2929/1153 这类）或新增 opcode 一旦激活，旧产物全部作废。所以 key 应该是：

```
(code_hash, spec_id, revmc_version, opt_level)
```

`spec_id` 是共识正确性必需的；后两个是为了避免你升级 revmc 或改优化等级之后，还在用旧编译器的产物——尤其在做落盘缓存的时候，这是必须的。

## 5. 落盘跨进程复用：v1 别做

收益是节点重启后的 warmup 期。但你的热集合可能只有几十上百个 code hash，后台线程几秒内就能重新编译出来——先量一下这个 warmup 期到底损失了什么，再决定要不要为它引入下面这些代价：

- **dlopen 一个 .so 就是执行任意代码**。缓存目录变成代码注入面，权限、校验和都得管起来。而且要立个死规矩：**编译产物永远不从 peer 同步**，否则就是供应链后门。
- 上千个 .so 的 fd 和地址空间占用，得改成懒加载或者打包成单个归档。

YAGNI：v1 纯内存 JIT。落盘留到有实测数据支撑再说。

## 6. 并发：两个 map 要分开处理，它们的读写比完全不同

`hot` 和 `count` 长得像，但特性相反：

**`hot`：读极多写极少**（只在编译完成时写，大概每秒个位数）。用 `RwLock<HashMap>` 也能跑，但每次调用的读锁仍是一次原子 RMW，多核下 cache line 会来回弹。这是教科书级的 read-mostly 场景，用 `ArcSwap<HashMap>` 做 copy-on-write：读者完全 wait-free、零竞争，写者克隆整个 map——map 才几百项，每秒克隆几次毫无压力。

**`count`：每次调用都写**——这个才是真瓶颈，共享 map 在并行执行下必然炸。方案：**per-worker 线程本地计数器，定期合并**（block 结束时，或每 N 毫秒）。计数本来就是启发式，丢几个数、稍微不准，完全无所谓。这样热路径上一个跨线程共享都没有。

另外两个小优化：

- **别用 SipHash 去 hash 一个 keccak 输出**。code hash 本身已经是均匀分布的，直接取前 8 字节当 hash 值（`nohash-hasher` 之类）。这是白捡的。
- 更进一步：如果 revm 的 `Bytecode` 是 `Arc` 共享的，可以把"已编译"的指针挂在 bytecode 对象上，热路径退化成一次指针解引用，连哈希查找都省了。需要动 revm 内部，看你能不能接受这个耦合。

## 7. 草稿里没有、但会咬人的几个坑

**编译失败没有出路。** 不支持的 opcode、LLVM 内部错误、编译超时——草稿里没有失败分支，结果就是这个 code hash 每次撞阈值都重新排队编译一次，无限重试。需要**负缓存**：失败的 key 标记为 permanently-cold，附带失败原因和一个（可选的、按 revmc 版本重置的）过期策略。

**per-block gas 记账是共识风险的重灾区。** revmc 为了性能会做基本块级的 gas/栈/内存扩展检查合并，而不是每条指令一次。这在语义上大部分时候等价（OOG 反正烧光 gas），但 `GAS` opcode 会观测到块中间的 gas 值，编译器必须在这些点切分基本块。这类边界条件出错就是直接的共识分叉。**这是整个方案里最危险的地方**，而且不是你的代码出的错，是上游的。所以必须有差分测试兜底（见下）。

**Inspector / tracer 完全不兼容。** native code 产生不了逐 opcode 回调。只要挂了 inspector（`debug_traceTransaction`、gas 分析、任何 hook），就必须强制走解释器。很容易漏，漏了就是功能回归。

**LRU 淘汰会 use-after-free。** 正在执行的 native code 被淘汰释放 → segfault。编译产物必须 `Arc<CompiledModule>`，进入 frame 时 clone 一份 Arc 持住，或者用 epoch-based reclamation。

**bailout 恢复路径。** revmc 遇到需要重入 host 的场景（CALL 之类）会把控制权交回来，恢复时的 interpreter state 必须严格一致。这块的测试覆盖要专门写。

**可观测性。** 上线后必须能回答"这层到底有没有用"：native vs interp 的调用比例、tier-up 速率、编译耗时直方图、编译失败计数、缓存命中率。没这些指标，你没法证明这个功能是正收益。

**测试策略——这是唯一能建立信心的东西。** 加一个 differential 模式：每笔交易同时跑解释器和 native，断言 `(result, gas_used, state diff, logs)` 完全一致。用它做三件事：CI 里跑固定 fixture；影子节点上跑真实链上流量；把阈值强制设成 1（全部编译）回放历史区块，把覆盖率拉满。再加一个随机字节码 fuzzer 对拍。

```rust
//! EIP-1559 fee market calculations.

use core::cmp::Ordering;

/// EIP-1559 `BASE_FEE_MAX_CHANGE_DENOMINATOR`: 每个区块 base fee 最多变动父块的 1/8。
const BASE_FEE_MAX_CHANGE_DENOMINATOR: u128 = 8;

/// EIP-1559 `ELASTICITY_MULTIPLIER`: 单块 gas 上限为 target 的 2 倍。
const ELASTICITY_MULTIPLIER: u64 = 2;

/// 按 EIP-1559 计算给定父块之后那个区块的 base fee。
///
/// 所有除法都是向下取整，与参考实现一致。中间乘积加宽到 `u128`：在 30M gas 的满块里，
/// `parent_base_fee * gas_delta` 在 base fee 超过约 1230 gwei 时就会溢出 `u64`，
/// 而主网到过这个量级。
pub fn next_base_fee(parent_base_fee: u64, parent_gas_used: u64, parent_gas_limit: u64) -> u64 {
    let target = parent_gas_limit / ELASTICITY_MULTIPLIER;

    // target 为 0 谈不上弹性，且会让下面除零。合法 header 走不到这里（gas limit 下限是
    // 单独校验的），但这条路径吃的是不可信输入，所以让费率保持不变，而不是 panic。
    if target == 0 {
        return parent_base_fee;
    }

    match parent_gas_used.cmp(&target) {
        Ordering::Equal => parent_base_fee,

        Ordering::Greater => {
            let delta = (u128::from(parent_base_fee) * u128::from(parent_gas_used - target))
                / u128::from(target)
                / BASE_FEE_MAX_CHANGE_DENOMINATOR;

            // 只要 `parent_base_fee * overshoot < 8 * target`，这个除法就会向下取整成 0：
            // 任何费率下的轻微超出都算，而当费率贴近地板时是*每一次*超出都算
            // （7 wei 配 15M target 时恒为 0）。没有这个下限，base fee 会在任意多个
            // 超 target 的区块里纹丝不动，所以 EIP-1559 强制至少涨 1 wei。
            let delta = u64::try_from(delta.max(1)).unwrap_or(u64::MAX);

            parent_base_fee.saturating_add(delta)
        }

        Ordering::Less => {
            let delta = (u128::from(parent_base_fee) * u128::from(target - parent_gas_used))
                / u128::from(target)
                / BASE_FEE_MAX_CHANGE_DENOMINATOR;

            // `target - parent_gas_used <= target`，故 `delta <= parent_base_fee / 8`：
            // 转换无损，减法不会下溢。不设下限，费率可以一路衰减到 0。
            parent_base_fee - delta as u64
        }
    }
}
```

1. **`u128` 中间量**：`parent_base_fee * gas_delta` 用 u64 会真溢出——30M 满块下 base fee 超过约 1230 gwei 就爆，2021 年的 mint 高峰摸到过。reth 也是这么加宽的。
2. **`max(1)` 那段**：就是你踩过的坑。补充一点，它比"超出一丁点"更凶的场景是 base fee 贴地板时——7 wei 配 15M target，`base_fee * overshoot` 永远小于 `8 * target`，delta 恒为 0，费率永远爬不起来。注释里写的是通式 `base_fee * overshoot < 8 * target`，方便你回头写测试直接照着挑边界值。
3. **`target == 0`**：我选了返回原值而不是 panic，因为除零在整数除法里会直接炸，而 header 校验吃的是 peer 来的数据。如果你想和 geth/reth 严格对齐（它们这里都会 panic，靠 gas limit 校验兜住），把那个 early return 换成 `debug_assert!(target > 0)` 即可。

```rust
#[inline]
fn bytes_to_nibbles_scalar(bytes: &[u8]) -> Vec<u8> {
    let mut out = Vec::with_capacity(bytes.len() * 2);
    for b in bytes {
        out.push(b >> 4);
        out.push(b & 0x0f);
    }
    out
}

#[cfg(any(target_arch = "x86_64", target_arch = "x86"))]
#[target_feature(enable = "avx2")]
unsafe fn bytes_to_nibbles_avx2(bytes: &[u8]) -> Vec<u8> {
    #[cfg(target_arch = "x86")]
    use std::arch::x86::*;
    #[cfg(target_arch = "x86_64")]
    use std::arch::x86_64::*;

    let len = bytes.len();
    let mut out: Vec<u8> = Vec::with_capacity(len * 2);
    let src = bytes.as_ptr();
    let dst = out.as_mut_ptr();

    let mask = _mm256_set1_epi16(0x0f0f);

    let mut i = 0;
    while i + 16 <= len {
        // vpmovzxbw: 16 字节零扩展成 16 个 u16, 第 j 个 lane 的值就是 bytes[i + j]。
        let wide = _mm256_cvtepu8_epi16(_mm_loadu_si128(src.add(i) as *const __m128i));

        // 每个 lane 构造成 ((b & 0x0f) << 8) | (b >> 4)。
        // 小端存回内存后, 低字节(高 nibble)先落地, 高字节(低 nibble)随后 —— 正好是要的顺序。
        let spread = _mm256_or_si256(_mm256_slli_epi16(wide, 8), _mm256_srli_epi16(wide, 4));
        let nibbles = _mm256_and_si256(spread, mask);

        // 每轮恰好写 32 字节, 上面 while 条件保证不越过 len * 2 的容量。
        _mm256_storeu_si256(dst.add(i * 2) as *mut __m256i, nibbles);
        i += 16;
    }

    while i < len {
        let b = *src.add(i);
        dst.add(i * 2).write(b >> 4);
        dst.add(i * 2 + 1).write(b & 0x0f);
        i += 1;
    }

    out.set_len(len * 2);
    out
}

pub fn bytes_to_nibbles(bytes: &[u8]) -> Vec<u8> {
    #[cfg(any(target_arch = "x86_64", target_arch = "x86"))]
    {
        // 你已经开了 target-cpu=native, cfg! 会在编译期折成 true,
        // 整个分发连同运行时探测一起消失; 换台没 AVX2 的机器才走 is_x86_feature_detected。

            // SAFETY: 上面刚确认 AVX2 可用;函数内所有写入都在 with_capacity 预留的
            // len * 2 字节内, set_len 前每个字节都已初始化。
            return unsafe { bytes_to_nibbles_avx2(bytes) };
        }
    }
    bytes_to_nibbles_scalar(bytes)
}
```

## 定下来的叫法

| 概念 | canonical | 废弃 |
|---|---|---|
| 一段字节码,以 code hash 为身份 | **Bytecode** | 合约、代码段 |
| 字节码装在某个地址上的实例 | **Deployment** | 热点合约、合约实例 |

两个判断依据:

- **「热点合约」必须废掉**,不是因为啰嗦,是因为它指错了对象。一个 bytecode 对应 N 个地址,而计数和缓存只有一份 —— 说「这个合约是热点」在工厂池子的场景里根本没有唯一指代。地址侧留 **Deployment** 这个词,是为了让人在真的想说地址时有词可用,否则迟早退回「热点合约」。
