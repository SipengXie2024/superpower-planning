## 先说一句必须说的：写库那层是干净的，丢数据在 fetch

我把你们三条都写了，但在贴之前有一个算术必须摆出来，因为它决定周五那批数对不对。

**你自己贴的日志行就是判决书。** `writer.rs` 里那条 `info!(from, to, rows = logs.len(), "range done")` 打的是 **Rust 里 `logs` 这个切片的长度**，跟 Postgres 一点关系没有。日志打出 `rows=0`，意味着 `write_range` 被调用时切片本来就是空的 —— COPY 那个分支被 `if !logs.is_empty()` 直接跳过了，Postgres 根本没拿到东西，也就无从"吞掉"。

三条独立佐证：

| 证据 | 说明 |
|---|---|
| `copy_batches_total` = 113,636 | 117,048 − 3,412 = **113,636**，分毫不差。COPY 对这 3,412 个 range 一次都没执行过 |
| 事务原子性 | COPY 和 `ranges_done` 的 INSERT 在**同一个事务**里。事务若被回滚，`ranges_done` 那行也不会留下 —— 你库里有那行，就证明事务提交了 |
| `copy.finish().await?` | 就算 COPY 报错，`?` 会直接 return，INSERT 不执行，`range done` 这行日志也压根打不出来。但它打出来了 |

反过来，超时那条路是对得上的：

```
04:11:55.318 WARN  request timed out      from=31541248 to=31541375
04:11:56.883 INFO  range done rows=0      from=31541248 to=31541375   ← 同一个 range
```

而你 SQL 查出来的第一行，`31541248 | 0 | 2026-09-02 04:11:56.883+00` —— **毫秒级对上了**。第二对 `31542016` 同样对得上。`rpc_timeouts_total` = 3,412 = 零行 range 数，一个不多一个不少，没有剩余需要别的原因来解释。

链路是这样的：`eth_getLogs` 超时 → fetch 返回 `Ok(Vec::new())`（**成功的空结果**）→ `with_retry` 看到 `Ok` 就不重试了，连 `retries_total` 都不加 → 空 vec 一路走到 writer → 标 done、`row_count=0`。

关于 `fetch_errors_total = 0`：超时那个分支加的是 `rpc_timeouts_total`，**代码里就没让它加 `fetch_errors_total`**。这个 0 是分支写法的产物，不是健康证明。而 `fetch.rs` 里"verifier 会兜底"那句注释也没有对应实现 —— `verify()` 只查连续覆盖，已经 done 的 range 永远不会被回头看。这是个注释声明了、但没人写的不变量。

丢失量：3,412 × ~10,600（1,204,551,903 / 113,636）≈ **3,600 万条 log**。

加池子不是坏事（16 个连接喂 24 个 worker 确实在排队，吞吐有损失），但它跟这次丢数据无关：sqlx 拿不到连接返回的是 `PoolTimedOut`，事务压根没开始，不可能留下 `ranges_done` 行；`pg_conn_errors_total` 也是 0。

```rust
pub enum FetchError {
    RateLimited,
    Timeout,              // ← 新增
    Rpc(String),
    Http(reqwest::Error),
    Exhausted,
}

pub async fn fetch_logs(client: &Client, from: u64, to: u64) -> Result<Vec<RawLog>, FetchError> {
    let body = json!({
        "jsonrpc": "2.0", "id": 1, "method": "eth_getLogs",
        "params": [{ "fromBlock": hex(from), "toBlock": hex(to) }],
    });

    match client.post(&CFG.rpc_url).json(&body).send().await {
        Ok(resp) => {
            let v: RpcResponse<Vec<RawLog>> = resp.json().await?;
            if let Some(err) = v.error {
                if err.code == -32005 {
                    return Err(FetchError::RateLimited);
                }
                return Err(FetchError::Rpc(err.message));
            }
            Ok(v.result.unwrap_or_default())
        }
        Err(e) if e.is_timeout() => {
            // 超时 ≠ 这段没有 log。必须当失败抛出去让 with_retry 重试，
            // 返回 Ok(vec![]) 会让 range 被静默标成 done 且 row_count=0。
            warn!(from, to, "request timed out");
            metrics::counter!("rpc_timeouts_total").increment(1);
            metrics::counter!("fetch_errors_total").increment(1);   // 让这个计数器别再骗人
            Err(FetchError::Timeout)
        }
        Err(e) => {
            metrics::counter!("fetch_errors_total").increment(1);
            Err(FetchError::Http(e))
        }
    }
}
```

## 周五那批数怎么补

`verify` 要等凌晨才跑，别等。改完直接手动清掉坏 range，让它们变成覆盖缺口：

```sql
-- 先留底
CREATE TABLE ranges_done_bad_20260914 AS
  SELECT * FROM ranges_done WHERE row_count = 0;

-- 确认这些段在 logs 里确实是空的（应该返回 0）
SELECT count(*) FROM logs l
  JOIN ranges_done_bad_20260914 b
    ON l.block_number BETWEEN b.from_block AND b.to_block;

-- 确认无误后再删
DELETE FROM ranges_done WHERE row_count = 0;
```

然后正常跑一轮 backfill —— 老的 `verify` 逻辑就能把它们认成缺口。带上 fetch 那个补丁的话这轮不会再丢；不带的话这 3,412 个里还会再掉 ~2.9%，得靠 verifier 每晚收敛三四轮，正好卡在周五上。

只上你那三条其实也能收敛（`DO UPDATE` + 重新入队确实会把数据补回来），但那是每晚一次的被动循环，每轮还在继续静默丢新数据，而且第 1 条那个 panic 永远不会响，只会给你一种"已经有断言守着了"的错觉。fetch 那 4 行才是让它不再发生的地方。

## 证据

**1. COPY 一批都没丢**（用你贴的数字）：

```
117048 (ranges_done) - 3412 (row_count=0) = 113636 = copy_batches_total
```

非空 range 数和 COPY 批次数**精确相等**。`logs_written_total / 113636 ≈ 10600 行/range`，跟日志里 7735~11048 那些行完全对得上。`pg_conn_errors_total = 0`。COPY 该跑的都跑了，写进去的都落盘了。

**2. 事务结构上也不可能**：`write_range` 里 COPY 和 `ranges_done` 的 INSERT 在**同一个 `tx`** 里。事务被静默回滚的话，`ranges_done` 那行**一起没了** —— 你会看到一个 gap，而不是一条 `row_count = 0` 的 done 记录。"COPY 丢了但 range 标成 done" 这个状态，从这段代码里根本走不出来。同理 `ON CONFLICT DO NOTHING` 也是无辜的：它只在冲突时触发，这 3,412 条是首次插入，`row_count` 是 `logs.len()` 绑上去的 —— 写进去的时候 `logs` 就是空的。而且 `if !logs.is_empty()` 这个 guard 意味着这些 range **压根没调用过 COPY**。

**3. 日志里因果链是直连的**，不是相关性：

```
04:11:55.318 WARN  request timed out  from=31541248 to=31541375
04:11:56.883 INFO  range done         from=31541248 to=31541375 rows=0   ← DB 里第 1 条，finished_at 04:11:56.883
04:11:58.004 WARN  request timed out  from=31542016 to=31542143
04:11:59.106 INFO  range done         from=31542016 to=31542143 rows=0   ← DB 里第 2 条，finished_at 04:11:59.106
```

同一个 range、同一个时间戳、相隔 1.5 秒。你截的这段日志里**超时的 range 和零行的 range 是同一批，一个不多一个不少**。

**4. `fetch_errors_total = 0` 是个假象**：超时分支只 `increment` 了 `rpc_timeouts_total`，然后 `return Ok(Vec::new())` —— 它从定义上就不可能让 `fetch_errors_total` 动。这个 0 不是"抓取层没出错"的证据，它不携带任何信息。同理 `retries_total = 8877` 里一次超时重试都没有，因为 `with_retry` 看到的是 `Ok`。

## 链路

```
20s 超时 → Ok(Vec::new())        ← fetch.rs，把失败伪装成"成功且为空"
        → with_retry 看到 Ok，不重试
        → normalize([]) = []
        → write_range 跳过 COPY，写 row_count = 0，标 done
        → verify 看到覆盖连续，无 gap
```

那句注释 `// 超时的 range 后面 verifier 会兜底` 正好说反了：verifier 只能捞**不在 `ranges_done` 里**的段，而超时路径干的事就是往 `ranges_done` 里写一条 done —— 它亲手毁掉了 verifier 唯一的线索。兜底机制对 `Err` 是有效的（不写 ranges_done → 连续性断裂 → 被捞回来重灌），被 `Ok(vec![])` 精确绕过。

### 2. `src/retry.rs`

`Timeout` 会自动落进通用重试臂，但这个函数有两处得顺手修掉，否则修复效果打折：

```rust
pub async fn with_retry<F, Fut, T>(mut f: F) -> Result<T, FetchError>
where
    F: FnMut() -> Fut,
    Fut: Future<Output = Result<T, FetchError>>,
{
    const MAX_DELAY: Duration = Duration::from_secs(30);
    let mut delay = Duration::from_millis(200);

    for attempt in 0..=CFG.max_retries {
        match f().await {
            Ok(v) => return Ok(v),
            Err(e) => {
                if attempt == CFG.max_retries {
                    // 原来这里会退化成 Exhausted，调用方就分不清这个 range 是超时
                    // 还是 RPC 报错了。直接把真实错误抛出去。
                    metrics::counter!("ranges_failed_total", "reason" => e.reason()).increment(1);
                    return Err(e);
                }
                metrics::counter!("retries_total", "reason" => e.reason()).increment(1);
                warn!(?e, attempt, "retrying");

                // 限流起步退避长一点，别顶着 429 猛打
                let d = if matches!(e, FetchError::RateLimited) {
                    delay.max(Duration::from_secs(1))
                } else {
                    delay
                };
                tokio::time::sleep(jittered(d)).await;
                delay = (delay * 2).min(MAX_DELAY);   // 原来无上限
            }
        }
    }
    Err(FetchError::Exhausted)   // 不可达，留着兜底
}

/// 全同步退避会让 24 个 worker 在同一毫秒一起重试，正好把 RPC 再打挂一次。
/// 取 [0.5d, 1.0d]，不引新依赖。
fn jittered(d: Duration) -> Duration {
    let ms = d.as_millis().max(1) as u64;
    let n = SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .unwrap_or_default()
        .subsec_nanos() as u64;
    Duration::from_millis(ms / 2 + n % (ms / 2 + 1))
}
```

### 2. `src/retry.rs`

改完 fetch 之后超时会自动走到现有的重试分支，这里只做三件小事：加 jitter（24 个 worker 退避曲线完全同步会打成脉冲）、给退避封顶、把"重试耗尽"单独计数。**没有改可重试错误的分类**，保持原来"什么错都重试"的语义，减少这次上线的变量。

```rust
pub async fn with_retry<F, Fut, T>(mut f: F) -> Result<T, FetchError>
where
    F: FnMut() -> Fut,
    Fut: Future<Output = Result<T, FetchError>>,
{
    let mut delay = Duration::from_millis(200);
    for attempt in 0..=CFG.max_retries {
        match f().await {
            Ok(v) => return Ok(v),
            Err(e) => {
                if attempt == CFG.max_retries {
                    metrics::counter!("retries_exhausted_total").increment(1);
                    warn!(?e, attempt, "giving up on range");
                    return Err(e);   // 返回真实错因，不再是笼统的 Exhausted
                }
                metrics::counter!("retries_total").increment(1);
                warn!(?e, attempt, "retrying");
                let jitter = Duration::from_millis(rand::random::<u64>() % 250);
                tokio::time::sleep(delay + jitter).await;
                delay = (delay * 2).min(Duration::from_secs(10));
            }
        }
    }
    Err(FetchError::Exhausted)
}
```

```rust
    let mut cursor = start;

        let (f, t) = (f as u64, t as u64);

        if f > cursor {
            gaps.push((cursor, f - 1));
        }

        // 标了 done 却一行都没有的 range 也算洞。Base 上 128 个区块
        // （约 4 分钟）平均 ~10k 条 log，真正的空 range 不存在。

            zero_ranges += 1;
            gaps.push((f.max(start), t.min(head)));
        }

        cursor = cursor.max(t + 1);
    }

    if cursor <= head {
        gaps.push((cursor, head));
    }

    metrics::gauge!("verify_zero_row_ranges").set(zero_ranges as f64);
    Ok(merge_ranges(gaps))
}

/// 排序后合并相邻/重叠区间，避免同一段被重灌两次
fn merge_ranges(mut gaps: Vec<(u64, u64)>) -> Vec<(u64, u64)> {
    gaps.sort_unstable();
    let mut out: Vec<(u64, u64)> = Vec::with_capacity(gaps.len());
    for (f, t) in gaps {
        match out.last_mut() {
            Some(last) if f <= last.1.saturating_add(1) => last.1 = last.1.max(t),
            _ => out.push((f, t)),
        }
    }
    out
}
```

```diff
             gaps.push((cursor, f - 1));
         }
+        if row_count == 0 && t >= cursor {
+            gaps.push((f.max(cursor), t));
+        }
         cursor = cursor.max(t + 1);
     }
     if cursor <= head {
         gaps.push((cursor, head));
     }
     gaps
 }
```

这条配合第 2 条（`DO UPDATE`）确实能把已经落库的 3,412 个 range 自动补回来——这是三条里唯一真正产生效果的。但它是**每天凌晨才修一次的事后补救**，中间那一天 dbt 读到的还是缺口数据；而且不修 fetch 的话，每天新灌的量里还会持续按同样比例长出新的空 range。

## 关于 pool

**不用调大，16 → 24~26 就够，32 也行但没意义。**

- 没有任何排队证据：`pg_conn_errors_total = 0`，COPY 批次数和非空 range 数完全对得上，没有超时或丢批。
- 每个 worker 在整个 `COPY + INSERT` 事务期间独占一条连接，所以 **pool ≥ concurrency 就已经消除排队**。我建议 `pg_pool_size = 26`（24 个 worker + 2 条留给 verify / metrics 那些旁路查询，免得它们跟 worker 抢）。
- 再往上是负收益：24~32 个并发 writer COPY 进同一张表，瓶颈会转到 WAL 和 heap extension 的锁上，加连接只是让更多请求堵在同一个地方。想提吞吐应该动 `batch_size` 或 `concurrency`，而且要配着测。

顺带一提，改完 fetch 之后超时会真的走重试，RPC 请求量会比现在略涨（3,412 次超时 × 最多 5 次重试，相对 1,498 万总量可以忽略）。如果 Alchemy 那条链路超时确实是日常，把 `request_timeout` 从 20s 提到 30s 能让大部分超时在第一次重试前就消失。

## 一个可选的小补丁

第 3 条有个副作用：fetch 修好之后，剩下那些**真的**没有 log 的 range（Base 上 128 个区块全空极其罕见，但不是不可能）会每天晚上被无限重灌一次。加个上限：

### 2. `src/retry.rs` —— 让超时真的被重试，且失败时把原因带出去

```rust
pub async fn with_retry<F, Fut, T>(mut f: F) -> Result<T, FetchError>
where
    F: FnMut() -> Fut,
    Fut: Future<Output = Result<T, FetchError>>,
{
    const MAX_DELAY: Duration = Duration::from_secs(30);
    let mut delay = Duration::from_millis(200);

    for attempt in 0..=CFG.max_retries {
        match f().await {
            Ok(v) => return Ok(v),
            Err(e) if !e.is_retryable() => return Err(e),
            Err(e) if attempt == CFG.max_retries => {
                metrics::counter!("retries_exhausted_total").increment(1);
                error!(?e, attempts = attempt + 1, "放弃该 range");
                // 调用方拿到 Err 绝对不能把这个 range 写进 ranges_done
                return Err(FetchError::Exhausted(Box::new(e)));
            }
            Err(e) => {
                metrics::counter!("retries_total").increment(1);
                warn!(?e, attempt, "retrying");
                // 半抖动：24 个 worker 同时被限流时不要同步重试
                let half = delay.as_millis() as u64 / 2;
                let jitter = half + rand::thread_rng().gen_range(0..=half);
                tokio::time::sleep(Duration::from_millis(jitter)).await;
                delay = (delay * 2).min(MAX_DELAY);
            }
        }
    }
    unreachable!("attempt == max_retries 分支一定会 return")
}
```

单次超时率 2.9%，重试 5 次后残留 ≈ 0.029⁵ ≈ 2×10⁻⁸，基本归零——**前提是超时是随机的**。如果某些 range 因为 log 太多而必然超过 20s，重试多少次都没用，所以配置里我把 `request_timeout` 也调了（见下）。

```rust
    tx: &mut Transaction<'_, Postgres>,

    to: u64,

            "COPY logs (block_number, tx_index, log_index, address, topic0, topics, data) \
             FROM STDIN WITH (FORMAT csv)"
        ).await?;
        copy.send(encode_csv(logs).as_bytes()).await?;
        let copied = copy.finish().await?;

        if copied != logs.len() as u64 {
            metrics::counter!("copy_row_mismatch_total").increment(1);
            // 这里没有 panic：返回 Err 会让整个事务回滚，range 不会进 ranges_done，
            // 下一轮自然重做。panic 在 tokio worker 里只会干掉这个 task（如果

            // 换不来任何额外保护，只会让剩下 23 个 worker 的进度一起没。
            return Err(sqlx::Error::Protocol(format!(
                "COPY row mismatch: range {from}..{to} expected {} got {copied}",
                logs.len()
            )));
        }
        metrics::counter!("copy_batches_total").increment(1);
        metrics::counter!("logs_written_total").increment(copied);
    }

    sqlx::query(
        "INSERT INTO ranges_done (from_block, to_block, row_count, confirmed_empty, finished_at) \
         VALUES ($1, $2, $3, $4, now()) \
         ON CONFLICT (from_block) DO UPDATE \
            SET to_block       = EXCLUDED.to_block, \
                row_count      = EXCLUDED.row_count, \
                confirmed_empty = EXCLUDED.confirmed_empty, \
                finished_at    = EXCLUDED.finished_at"
    )
    .bind(from as i64)
    .bind(to as i64)
    .bind(logs.len() as i64)
    // 走到这里还是空，说明 RPC 真的返回了 []（超时现在会在 fetch 层报错），
    // 标记一下，verify 就不会每晚把它当可疑 range 反复重灌。
    .bind(logs.is_empty())
    .execute(&mut **tx)
    .await?;

    Ok(())
}
```

如果你确实想让行数不一致变成致命错误，在 worker 那层对 `copy_row_mismatch` 做 `std::process::exit(1)` 就行，不要在这里 panic。

```rust
pub async fn verify(pool: &PgPool, start: u64, head: u64) -> Result<Vec<(u64, u64)>, sqlx::Error> {
    let rows = sqlx::query_as::<_, (i64, i64, i64, bool)>(
        "SELECT from_block, to_block, row_count, confirmed_empty \
         FROM ranges_done ORDER BY from_block"
    ).fetch_all(pool).await?;   // 原来是 .unwrap()，verifier 半夜 panic 没人会知道

    let mut gaps = Vec::new();
    let mut cursor = start;

    for (f, t, row_count, confirmed_empty) in rows {
        let (f, t) = (f as u64, t as u64);

        // 覆盖空洞（原有逻辑）
        if f > cursor {
            gaps.push((cursor, f - 1));
        }

        // Base 上连续 128 个区块一条 log 都没有基本不可能，
        // row_count = 0 且没被确认过就当可疑，扔回去重灌。
        if row_count == 0 && !confirmed_empty {
            gaps.push((f, t));
            metrics::counter!("suspect_empty_ranges_total").increment(1);
        }

        cursor = cursor.max(t + 1);
    }

    if cursor <= head {
        gaps.push((cursor, head));
    }

    gaps.sort_unstable();
    gaps.dedup();
    Ok(gaps)
}
```

## ⚠  一条关于你原方案的告警

**第 2 条绝对不能脱离第 1 条单独上线。** 如果保留 `ON CONFLICT DO NOTHING` 而只加"row_count = 0 判为 gap"：重灌成功 → COPY 写入 8900 行 → `ranges_done` 冲突 → DO NOTHING → `row_count` 仍然是 0 → 第二天再判可疑 → 再写 8900 行。每晚往 `logs` 里重复灌约 3600 万行，永不停止。上面的 `DELETE ... BETWEEN` 是第二道保险。

## 关于 pool 要不要再加大

**不要，26 就够，别超过 28。** 理由：

- 24 个 worker 最多同时占 24 条连接，池子开到 32 有 8 条永远闲着，只是白占 Postgres 后端内存（每条 5–10MB）。
- 16→26 本身无害，可以上，但它**不会改变任何一个 row_count**。池子排队的表现是 `PoolTimedOut` 错误，而 `pg_conn_errors_total = 0`；而且 24 个 worker 的绝大部分墙上时间花在几秒级的 RPC 上，16 条连接大概率从来没被打满过。
- 单表 COPY 的瓶颈是 WAL / 磁盘，不是连接数。并发写手再多只会加剧锁和 WAL 竞争，反而更慢。真嫌写得慢，动 `copy_chunk_rows` 或者给 `logs` 按 block_number 做分区，别动池子。

    let rows = sqlx::query_as::<_, (i64, i64)>(
        "SELECT from_block, to_block FROM ranges_done ORDER BY from_block"
    ).fetch_all(pool).await.unwrap();

    // 只检查 [start, head] 被 ranges_done 连续覆盖，没盖到的段报出来重灌
    let mut gaps = Vec::new();
    let mut cursor = start;
    for (f, t) in rows {
        let (f, t) = (f as u64, t as u64);
        if f > cursor {
            gaps.push((cursor, f - 1));
        }
        cursor = cursor.max(t + 1);
    }
    if cursor <= head {
        gaps.push((cursor, head));
    }
    gaps
}
