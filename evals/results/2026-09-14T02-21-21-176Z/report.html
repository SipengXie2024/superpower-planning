## 三、几点分析，省得你回来重推

**1. gas 差值是症状，不是独立的计费 bug。**

MCOPY 的 gas 只取决于栈上的 `dst/src/len`，跟内存里的数据无关。所以 memcpy 写花数据本身不会直接改 gas —— 1743 这个差值只能来自下游：要么污染的数据改变了后续控制流（分支/SSTORE/CALL 走向不同），要么被写坏的字回流成了后面某条内存指令的操作数。

这条推论有两个用处：

- 它解释了为什么换成 memmove 之后单跑就对上了 —— 数据对了 gas 自然跟着对。你那个修复方向基本可以确认是对的。
- 反过来，**1743 不能拿来当"计费代码"的回归信号**。你顺手动的那段扩容计费是一个独立改动，它可能既没被这个复现覆盖，又正好是两个红测试的来源。

**所以回来第一件事：把这两处改动拆成两个 commit。** memmove 那个已验证，扩容计费那个未验证。现在缠在一起，等于让一个已知好的修复替一个未知的改动背锅。拆开之后 `git stash` 掉计费那半边再跑 `cargo test -p revmc`，能立刻判断红的是不是它。

**2. 两个红测试很可能是同一个根因。**

`test_mcopy_zero_len` 和 `test_memory_expansion_gas` 同时红，指向扩容计费里 len=0 的处理。按 EIP-5656，`MCOPY` 在 `len == 0` 时是 no-op：**不触发内存扩容，也不因为 `dst`/`src` 越界而收费**。如果改动后变成对 `max(dst+len, src+len)` 无条件算扩容，len=0 时就会错误地按 offset 收一笔 —— 这一条能同时解释两个失败。

顺带一个值得确认的点：扩容必须按 `max(dst+len, src+len)` 算，`src` 和 `dst` 两边都要。如果原来的 codegen 只按 `dst` 算扩容，那是藏在同一片代码里的第二个 bug，和重叠问题无关，但会独立造成 gas 不符。

对账用的公式：
- `Cmem(words) = 3*words + words²/512`，按当前 size 到新 size 的**差值**收
- MCOPY 总计 `3 + 3*ceil(len/32) + 扩容差值`

**3. 一个便宜的诊断：1743 = 3 × 581，整除。**

581 字正好是 18592 字节。这可能是巧合，但复制字费和扩容费在这个数量级下量纲不同，算一下 581 字这个解释能不能对上那笔交易的实际 len，可以快速区分"少算了 581 个字的复制费"和"扩容差值算错"。花不了十分钟。

**4. EXTCODECOPY 那个猜想，方向大概率是错的，但附近有真问题。**

`EXTCODECOPY` / `CODECOPY` / `CALLDATACOPY` / `RETURNDATACOPY` 都是从**非内存**来源（账户代码、calldata、returndata）拷进内存，两边不同地址空间，按定义不会重叠。所以直接照搬 MCOPY 的重叠假设，多半跟不出东西。

但有个 revm 特有的坑值得真去看一眼：**revm 用的是跨调用帧的 `SharedMemory`**。如果 revmc 沿用了这个结构，那么 `CALLDATACOPY` / `RETURNDATACOPY` 的源可能是调用方内存在同一个 buffer 里的切片，而目标又在同一个 buffer 里 —— **这种情况下源和目标是真的可能重叠的**。

所以建议把那几处 grep 结果的优先级改一下：先确认 revmc 的拷贝 helper 是否存在源/目标共用 arena 的情况（`SharedMemory` 或任何共享 scratch buffer），有的话真正的风险点是 `CALLDATACOPY`/`RETURNDATACOPY`，不是 `EXTCODECOPY`。

这一条我没法验证——代码不在，你回来自己确认一下 revmc 是不是真的用了 `SharedMemory`。

### `test_mcopy_zero_len`

按 EIP-5656，`len == 0` 的 `MCOPY` 是 no-op：只收 3 gas 的固定费，**不收 memory expansion**，
offset 多大都不收。EVM 里零长度内存访问从不撑大 memory。

最经典的写坏方式：无条件按 `max(dst + len, src + len)` 算扩容边界，并且在 `len == 0` 检查
**之前**就计了费。如果你那处扩容编辑挪走或删掉了零长度的 guard，出来的正好是这个失败。
去确认 `len == 0` 的 early-out 发生在扩容成本计算**之前**。

### `test_memory_expansion_gas`

`MCOPY` 摸两个区间，扩容只能按两者的高水位 `max(dst + len, src + len)` 收**一次**。
两种都符合症状的写法：

- 按区间分别收（收了两次），或者
- 用 `max(dst, src) + len` —— 这跟 `max(dst + len, src + len)` 微妙地不同，只在特定
  offset 组合下才发散。

两种错误都会被 `words² / 512` 这个二次项放大，所以大 offset 下炸得很响，小 offset 下能过。
值得看一眼这个测试用的是哪一档。

### `EXTCODECOPY` —— 大概率**不是**同一个 bug

直说，可能给你省一天：`MCOPY` 是唯一一个两个操作数**都**在 EVM memory 里的 opcode。
`EXTCODECOPY` / `CODECOPY` 读的是 account code，`CALLDATACOPY` 读 calldata，
`RETURNDATACOPY` 读 return buffer —— 正常设计下这些都不与 EVM memory 别名，
所以那里用 `memcpy` 是真的安全，这个猜想八成是假警报。

唯一要查的例外：如果内层 call 的 return data buffer 是指进共享 memory arena 的一个 slice，
而不是自己独立分配的，那么 **`RETURNDATACOPY`** *确实*可能别名 memory。这一组里高风险的是它，
不是 `EXTCODECOPY`。去确认你 codegen 里 return buffer 怎么分配的；如果是 owned，
整个问题就可以关掉了。
