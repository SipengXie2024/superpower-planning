## 坑 0:先确认这事值不值得做

你草稿里所有问题都默认了"解释器 dispatch 是瓶颈"。对绝大多数真实合约,它不是。一笔 Uniswap swap 的时间主要花在 SLOAD/SSTORE 回落到 state provider、keccak、以及 trie/cache 查找上,这些走 native 也一样得跳回 host。JIT 真正吃掉的是 opcode 分发和栈操作那部分开销。

## 你的五个问题

### 1. 阈值:计数是错的单位,应该用累计 gas

固定次数阈值在两个方向上都会错。摊销条件是 `N × Δt > C`(Δt 是每次调用省下的时间,C 是编译成本):

- 一个热门 ERC20:单次执行 ~300µs,native 省 20% = 60µs;编译 ~50ms → 需要 **833 次**才回本。拍 50 会让你编译一堆永远回不了本的合约。
- 一个 ZK verifier:单次 5ms,native 省 50% = 2.5ms;编译 200ms → **80 次**就回本。但它可能一天才被调 60 次,按次数永远升不了级。

换成**累计 gas** 一次解决两个方向:gas 本身就是"干了多少活"的代理,贵的合约自然升得快。更准一点还可以把编译成本挂进去(LLVM 编译时间大致随 bytecode 长度超线性增长):

```
promote when  cumulative_gas[code_hash] > k * bytecode_len
```

附带一个白送的好处:**用 gas 当单位等于给"骗编译器"这件事定了价**。攻击者想逼你烧 CPU 做 LLVM 编译,必须先真金白银烧 gas,DoS 成本自动被链上定价了。用次数就没这个性质。

起步值:`k` 先调到让常见热合约跨 3~5 个区块才升级(以太坊主网量级大概对应累计千万级 gas),然后按上线后的实测曲线调。这个数必须是运行时可配的。

### 2. 编译绝对不能卡住当前交易

理由不只是延迟:一旦编译同步,**执行时间就变成了缓存状态的函数**,同一笔交易在冷/热节点上耗时差几个数量级,你的 benchmark、超时逻辑、出块截止时间全部失去可复现性。

异步,但要补三件你草稿里漏了的事:

- **去重**:从"跨过阈值"到"编译完成"之间,这个合约可能又被调 500 次,每次都会重新入队。状态机得是 `Cold → Queued → Compiling → Hot | Failed`,不是一个计数器。
- **有界队列 + 丢弃**:队列满了就跳过,不要无限堆积。
- **低优先级、独立线程池(1~2 个线程)**:编译不能跟执行抢 CPU。出块场景下这条尤其要命。

再加一个:**单合约编译超时**。24KB 的合约在 O2 下可能要几秒,超时就直接标记 `Failed` 并永久拉黑这个 code hash。

### 3. 落盘:v1 不要做

落盘看着是白捡的,实际上你买下了一个缓存失效问题,而失效的后果是**静默执行出错**。磁盘上的 key 必须包含 `(code_hash, spec_id, revmc 版本, LLVM 版本, opt level, target CPU features)`,少一个就可能加载到语义不匹配的产物。另外 `dlopen` 一个磁盘目录里的 `.so` 本身是个代码执行面。

建议:v1 纯内存。真要跨进程复用,更安全的形态是**离线 AOT 一批白名单合约**(Uniswap router/pool、USDC、WETH、Multicall 那 100 来个),当成构建产物或运维步骤跑,产物固定、可审计、可复现,运行时 JIT 只负责白名单之外的发现。这样冷启动问题解决了,运行时失效风险为零。

但这条取决于一个事实:**你们的进程是长期跑还是按任务起**?如果是每个模拟任务起一个短命进程,那内存缓存等于没有,离线 AOT 就从"可选"变成"唯一可行方案",整个设计要重来。

### 4. Reorg:不需要处理

这是个好消息。你的缓存 key 是 **code hash**,而 bytecode 对给定 code hash 是不可变的 —— reorg 改变不了 hash 到 bytecode 的映射。所以**编译产物永远不会被 reorg 作废**。

reorg 实际造成的只有两件事,都无害:

- 被回滚分支上部署的合约,它的编译产物变成死缓存 → LRU 自然淘汰。
- 热度计数统计了被回滚的执行 → 热度本来就是启发式,不准无所谓。

唯一的雷是:**如果你哪天改成按 address 做 key,以上全部失效**。那时 reorg、SELFDESTRUCT 后 CREATE2 原地重部署、EIP-7702 的 delegation 变更全都变成正确性事故。坚持用 code hash。

### 5. 两个 HashMap:是瓶颈,但改法不是换个并发 map

关键观察:`count` 是**每次调用都写**,`hot` 是每次调用都读、极少写。一个全局 `Mutex<HashMap>` 放在 `count` 上,等于给每次合约调用加一次全局锁竞争,并行执行下这比你省下来的 dispatch 开销还大。

但比"换成 DashMap"更好的做法是**把这两张表干掉,融进你已有的 code cache**:

执行前你本来就必须拿到 `Bytecode`(通常是从某个 `address/hash → Arc<Bytecode>` 的缓存里取)。把计数器和编译产物挂到**同一个 entry** 上:

```rust
struct CodeEntry {
    bytecode: Bytecode,
    hot_gas: AtomicU64,              // relaxed fetch_add,无锁
    compiled: ArcSwapOption<Compiled>, // 一次 atomic load
}
```

这样热路径上**一次额外的哈希查找都不需要** —— 你手里已经有 entry 了。计数是 relaxed 原子加,查编译产物是一次 atomic load。两个瓶颈同时消失,而且少维护两张表的生命周期。

如果 MHOT 没有这样一个 code cache,退而求其次:`hot` 用 `ArcSwap<HashMap>`(读者一次原子加载,写者罕见,整表 clone 也无所谓),`count` 用 **thread-local 计数器 + 每个区块末尾汇总**到共享 profile。热度是启发式,近似计数完全够用。

## 你没提到的坑

按严重程度排:

1. **cache key 必须包含 spec_id(硬分叉)。** 这是正确性 bug,不是优化问题。同一段 bytecode 在 Shanghai 和 Cancun 下语义不同(PUSH0、TLOAD/TSTORE、MCOPY、EIP-6780 改了 SELFDESTRUCT)。只按 code hash 做 key,一旦跨分叉边界重放历史区块就会执行错。

2. **差分测试是第一交付物,不是收尾工作。** 你需要一个 shadow 模式:native 执行完后按一定采样率用解释器重跑,比对 `(result, gas_used, state diff, logs)` 四元组完全一致。再加上用历史主网区块双引擎全量重放。这是整个项目里最重要的一块工程,比 JIT 本身重要。

3. **Kill switch。** 一个运行时开关能立刻全局关掉 native 路径,外加 per-code-hash 黑名单。生产上发现 miscompile 时你需要的是关开关,不是发版。

4. **编译产物的生命周期是内存安全问题。** `CompiledFn` 是指向 JIT 内存区的裸函数指针。如果 LRU 淘汰时有线程正在里面执行 → segfault。必须让调用方在整个调用期间持有 `Arc<Module>`(上面 `ArcSwapOption` 的设计正好给了你这个),或者用 epoch-based reclamation。

5. **内存上限。** LLVM 输出通常是 bytecode 的 10~50 倍。一万个热合约能吃掉几个 GB 的 RWX 页。要有总量硬上限 + LRU。

6. **panic 不能跨 FFI 边界。** 编译产物是 `extern "C"`,host callback 里 panic 穿过去就是 UB。所有回调边界要么 `catch_unwind`,要么确保无 panic。`[NEEDS-EVIDENCE]` revmc-builtins 覆盖了多少需要确认。

7. **热度要衰减。** 长期运行的节点上,半年前热过的合约计数还挂在那。每 N 个区块把所有计数右移一位就够了。

8. **LLVM 构建依赖。** revmc 需要 LLVM 17/18 作为构建依赖,这对 CI、交叉编译、二进制分发是实打实的运维成本,先确认你们能接受。

9. **`[NEEDS-EVIDENCE]` 几个需要你实测确认的 revmc 行为:** 基本块级 gas 预扣是否影响块中间 `GAS`(0x5A)opcode 的返回值;CALL 时 native 栈帧是嵌套还是跳回 host 顶层执行器(嵌套的话 1024 层调用深度可能爆机器栈,变成 segfault 而不是干净的 revert);AOT 模式的产物格式和加载方式。

10. **不要给 initcode 计数或编译。** CREATE/CREATE2 的 initcode 是一次性的,而且它的 hash 不是部署后代码的 hash。

/// Elasticity multiplier from EIP-1559: a block targets half of its gas limit.
const ELASTICITY_MULTIPLIER: u64 = 2;

/// The base fee moves by at most 1/8 of its previous value per block.
const BASE_FEE_MAX_CHANGE_DENOMINATOR: u128 = 8;

/// Computes a block's base fee from its parent's header fields, per EIP-1559.
///
/// The fee is unchanged when the parent hit its gas target exactly, rises when the
/// parent was over target, and falls when it was under, by at most 1/8 either way.
///
/// Three details the arithmetic hinges on:
///
/// * The upward delta is floored at 1, so a parent that sits barely over target
///   still moves the fee instead of stalling on an integer division that truncates
///   to zero. The downward branch has no such floor and no lower bound, which is
///   what lets the fee decay all the way to zero on an idle chain.
/// * `parent_base_fee * gas_used_delta` overflows `u64` at realistic mainnet values
///   (a ~2000 gwei fee against a 15M gas delta), so the product is taken in `u128`
///   and narrowed only after both divisions.
/// * A `parent_gas_limit` below [`ELASTICITY_MULTIPLIER`] makes the target zero.
///   Rather than divide by zero, the fee is returned unchanged; such a parent is
///   invalid on other grounds (the gas limit floor is 5000), so this only keeps the
///   function total against a malformed header.
pub fn next_base_fee(parent_base_fee: u64, parent_gas_used: u64, parent_gas_limit: u64) -> u64 {
    let parent_gas_target = parent_gas_limit / ELASTICITY_MULTIPLIER;

    if parent_gas_used == parent_gas_target || parent_gas_target == 0 {
        return parent_base_fee;
    }

    if parent_gas_used > parent_gas_target {
        let gas_used_delta = parent_gas_used - parent_gas_target;
        let delta = base_fee_delta(parent_base_fee, gas_used_delta, parent_gas_target);

        // Floor at 1: without it, a chain hovering just above target keeps its base
        // fee pinned forever because the delta truncates away.
        let delta = u64::try_from(delta.max(1)).unwrap_or(u64::MAX);
        parent_base_fee.saturating_add(delta)
    } else {
        let gas_used_delta = parent_gas_target - parent_gas_used;
        let delta = base_fee_delta(parent_base_fee, gas_used_delta, parent_gas_target);

        // `gas_used_delta <= parent_gas_target` on this branch, so the delta is at
        // most `parent_base_fee / 8`: the narrowing and the subtraction both hold.
        parent_base_fee - delta as u64
    }
}

/// `parent_base_fee * gas_used_delta / parent_gas_target / 8`, floored at every
/// division and kept in `u128` so the product cannot overflow.
fn base_fee_delta(parent_base_fee: u64, gas_used_delta: u64, parent_gas_target: u64) -> u128 {
    u128::from(parent_base_fee) * u128::from(gas_used_delta)
        / u128::from(parent_gas_target)
        / BASE_FEE_MAX_CHANGE_DENOMINATOR
}
```

pub fn bytes_to_nibbles(bytes: &[u8]) -> Vec<u8> {
    let len = bytes.len() * 2;
    let mut out = Vec::with_capacity(len);
    // SAFETY: `out` 刚以 `len` 容量分配，`nibbles_into` 恰好写满 `len` 个字节并
    // 全部初始化；u8 无 Drop，set_len 不会泄漏或读到未初始化内存。
    unsafe {
        nibbles_into(bytes, out.as_mut_ptr());
        out.set_len(len);
    }
    out
}

///
/// # Safety
/// `out` 必须可写入 `bytes.len() * 2` 个字节。
#[inline]
pub(crate) unsafe fn nibbles_into(bytes: &[u8], out: *mut u8) {

        if is_x86_feature_detected!("avx2") {

            return;
        }
    }

    unsafe { nibbles_scalar(bytes, out) }
}

/// # Safety
/// `out` 必须可写入 `bytes.len() * 2` 个字节。
#[inline]
unsafe fn nibbles_scalar(bytes: &[u8], out: *mut u8) {
    for (i, &b) in bytes.iter().enumerate() {
        // SAFETY: i < bytes.len()，故 2i+1 < bytes.len()*2，在调用方保证的范围内。
        unsafe {
            out.add(i * 2).write(b >> 4);
            out.add(i * 2 + 1).write(b & 0x0f);
        }
    }
}

/// 一次吃 16 字节，吐 32 个 nibble。
///
/// # Safety
/// 需要 AVX2；`out` 必须可写入 `bytes.len() * 2` 个字节。
#[cfg(target_arch = "x86_64")]
#[target_feature(enable = "avx2")]
unsafe fn nibbles_avx2(bytes: &[u8], out: *mut u8) {
    // 不走 shuffle 走 zero-extend：把 16 个字节零扩展成 16 个 u16（每个 = 0x00bb），
    // 此时每个 word 的低字节就是输出的偶数位、高字节就是奇数位（小端），于是
    //   hi = w >> 4          -> 低字节 = b >> 4
    //   lo = (w << 8) & 0x0f00 -> 高字节 = b & 0x0f
    // 或起来就地成序，不需要任何跨 lane 修正。
    //
    // 这里特意避开你说的 `_mm256_shuffle_epi8` + 交错：shuffle 和 unpack 都是
    // 128-bit lane 内操作，高低 nibble 交错回去还得补一条 `_mm256_permute4x64_epi64`，
    // 白搭一条跨 lane 指令（3 cycle latency）。cvtepu8_epi16 这条路短一截。
    let lo_mask = _mm256_set1_epi16(0x0f00u16 as i16);

    let mut i = 0usize;
    let blocks = bytes.len() / 16;
    for _ in 0..blocks {
        // SAFETY: i + 16 <= bytes.len()；输出 i*2 + 32 <= bytes.len()*2。
        unsafe {
            let x = _mm_loadu_si128(bytes.as_ptr().add(i) as *const __m128i);
            let w = _mm256_cvtepu8_epi16(x);
            let hi = _mm256_srli_epi16(w, 4);
            let lo = _mm256_and_si256(_mm256_slli_epi16(w, 8), lo_mask);
            _mm256_storeu_si256(out.add(i * 2) as *mut __m256i, _mm256_or_si256(hi, lo));
        }
        i += 16;
    }

    // 尾巴不足 16 字节。32 字节的 account hash 走不到这里。
    if i < bytes.len() {
        // SAFETY: 剩余 bytes.len()-i 字节，对应输出起点 out+i*2，仍在范围内。
        unsafe { nibbles_scalar(bytes.get_unchecked(i..), out.add(i * 2)) }
    }
}
```

`is_x86_feature_detected!` 来自 `std`（`no_std` 的话换 `std_detect`）。它内部缓存在 static 里，每次调用是一条 relaxed atomic load + 一个稳定预测的分支，千万级调用量下可以忽略。

### Q1：统计的主键是「地址」还是「code hash」？

**我的建议：以 code_hash 为主键，address 作为附属维度（存代表地址 + 地址计数）。**

理由：revmc 编译的对象是**字节码**，不是地址。而主网上代理模式极其普遍——Uniswap V2 的几十万个 pair、EIP-1167 minimal proxy 克隆出来的合约群、Safe 的海量 proxy 实例，它们共享同一份字节码。如果你按地址计数：

- 每个 pair 单独看都是「冷」的，排进不了 top N
- 但这份字节码合起来可能是全链执行次数最高的代码之一
- 结果就是：revmc 的编译名单里塞满了单个热门地址，而真正值得编译的「高复用字节码」被你的统计切碎了

反过来，DELEGATECALL 的情况也一样：proxy 地址被调用，实际跑的是 implementation 的代码。按地址归因，你数到的是 proxy（那几十字节的 delegate stub）；按 code hash 归因，你数到的才是真正在解释器里烧 CPU 的那份代码。

选项：
- **A（推荐）**：主键 `code_hash`，同时记录 `distinct_address_count` 和一个代表地址（方便人肉查证）
- **B**：主键 `(address, code_hash)` 二元组，把聚合权交给下游脚本——更灵活，但输出行数量级上升，全历史可能到亿级行
- **C**：就按地址，理由是你们的分层策略本来就是按地址挂载的

如果选 C，我需要知道：MHOT 里 revmc 的编译产物是按什么索引查的？如果是按 code hash 查（revmc 的常规做法），那 C 会导致统计口径和执行口径对不上。

**我的建议：所有会创建执行栈帧的场合都算，包括 revert 掉的。**

理由：你要衡量的是「解释器在这份字节码上烧了多少 CPU」，那就得看有多少次真的进了解释循环。具体有这么几类，我想确认你的口径：

| 场景 | 我的建议 | 为什么 |
|---|---|---|
| top-level tx 的 `to` | ✅ 算 | 无争议 |
| 内部 CALL / STATICCALL / CALLCODE | ✅ 算 | 不算的话 token、router、oracle 这类被内部调用为主的合约会被严重低估 |
| DELEGATECALL | ✅ 算，归给被执行的那份代码 | 见 Q1 |
| CREATE / CREATE2 的 initcode | ⚠  单独一列 | 它确实进了解释器，但 initcode 是一次性的，编译它没意义。建议单独统计而不是混进主计数 |
| 执行了但最终 revert 的帧 | ✅ 算 | CPU 已经烧掉了。revert 不退还你的执行时间 |
| 调用到 EOA / 空账户 | ❌ 不算 | 没有代码可执行 |
| 预编译合约 | ❌ 不算（或单独列） | 本来就是 native，revmc 编不了也不需要编 |
| EIP-7702 委托的 EOA | 看区块范围 | 如果扫到 Pectra 之后，这类账户的 code 是 delegation indicator，实际执行的是被指向的合约代码。需要和 DELEGATECALL 一样处理 |
